## 1. What This Is

A **standalone browser application** that demonstrates a privacy-preserving payment delegation chain using Zero-Knowledge proofs. It runs entirely client-side — no server, no build step, no framework. Open `index.html` in any browser.

### The Problem It Solves

In traditional payment delegation (Mastercard → PSP → Business → Agent → Merchant), every party can see every other party's limits and amounts. This creates privacy and competitive sensitivity issues.

**ZK proofs solve this:** each entity proves their allocation is valid without revealing the actual numbers to the chain or to downstream parties.

### The Analogy

Think of it like a bank issuing sealed envelopes:
- Mastercard seals their threshold in an envelope (commitment)
- PSP decides their own amount, asks Mastercard "is this OK?"
- Mastercard checks privately and stamps the PSP's request (signature) — without opening their envelope to show PSP what's inside
- The blockchain only sees sealed envelopes and stamps — never the numbers

## 3. Core Concepts

### 3.1 Commitment

A cryptographic "sealed envelope." Given a value `v` and a random blinding factor `b`:

```
commitment = SHA-256("poc-poseidon:" + v + ":" + b)
```

In production this would be the Poseidon hash (ZK-friendly). For the POC we use SHA-256 via the browser's `crypto.subtle.digest` API. The commitment goes on-chain. The value and blinding factor stay off-chain.

**Key property:** You cannot reverse a commitment to find `v` without knowing `b`. Two identical values with different blindings produce completely different commitments.

### 3.2 ZK Proof (Simulated)

In production: Groth16 proof on the BN128 elliptic curve, generated by snarkjs from a Circom circuit.

In this POC: `fakeProof()` generates random bytes in the exact Groth16 data structure:
```js
{
  pi_a: [hex32, hex32, "1"],
  pi_b: [[hex32, hex32], [hex32, hex32], ["1", "0"]],
  pi_c: [hex32, hex32, "1"],
  protocol: "groth16",
  curve: "bn128"
}
```

The proof structure is faithful to production. The cryptography is simulated. **The flows, data structures, approval logic, and rejection behaviors are all correct.**

### 3.3 Approval Signature (Core Conceptual Model)

This is the key design decision that makes the system privacy-correct:

**WRONG approach (naive):** Parent shares their threshold with child so child can check `childAmt ≤ parentThreshold`. This leaks the parent's threshold.

**CORRECT approach (implemented here):** 
1. Child decides their own amount independently
2. Child sends approval request to parent
3. Parent checks `childAmt ≤ parentThreshold` **privately in their own system**
4. Parent returns **only a signature** — never the threshold
5. ZK proof proves: `verify(parent_pubkey, signature, childCommitment) == true`
6. Chain verifies the proof — never sees either amount

In the POC, `requestApproval()` simulates steps 3-4. The parent's amount is used only inside that function for the comparison — it is **never written to child state**.

### 3.4 Nullifier

A one-time token preventing payment replay. Generated by the leaf (merchant-facing) entity:

```
nullifier = SHA-256("nullifier:" + entityId + ":" + invoiceSecret + ":" + amount)
```

Once registered on-chain, any attempt to reuse the same nullifier is rejected. This is the "tear-off receipt stub" — once used, gone forever.

### 3.5 Chain Linkage

Each entity's output commitment becomes the next entity's input commitment. This creates a verifiable delegation chain on-chain. The Groth16 verifier checks:

```
inputCommitment[i] === outputCommitment[i-1]   for all i > 0
```

## 4. Application State Model

Each entity in the chain is represented as a JS object:

```js
{
  id: UUID,                    // stable identifier
  name: string,                // display name ("Mastercard", "PSP", etc.)
  amt: string,                 // private amount — NEVER sent on-chain
  blinding: hex,               // random blinding factor — NEVER sent on-chain
  invoiceSecret: hex,          // used for nullifier derivation (leaf only)

  inCommitment: hex | null,    // PUBLIC: parent's output commitment (on-chain)
  outCommitment: hex | null,   // PUBLIC: this entity's commitment (on-chain)
  proof: ProofObject | null,   // PUBLIC: Groth16 proof (on-chain)
  nullifier: hex | null,       // PUBLIC: leaf entities only (on-chain)

  approved: boolean,           // has parent signed off?
  approvalSig: hex | null,     // signature from parent — ONLY thing child receives

  status: 'idle'|'gen'|'done'|'err',
  err: string | null,
}
```

**Critical invariant:** `approvalSig` contains only the signature. The parent's threshold, blinding factor, and amount are **never present in child state**.

## 5. User Flow

### Builder Tab (`/` — default)

```
Step 1: Root entity (Mastercard)
  → User enters amount (private)
  → Clicks "Generate Commitment & Proof"
  → outCommitment appears in Public zone
  → inCommitment of next entity is auto-populated

Step 2: Child entity (PSP)
  → Approval banner appears: "Request approval from Mastercard"
  → User enters their own amount (PSP decides this independently)
  → Clicks "Request approval"
  → requestApproval() runs:
      - Mastercard checks childAmt ≤ parentAmt privately
      - If OK: child.approved = true, child.approvalSig = <sig>
      - If not: child.err = "Denied. Threshold not disclosed."
  → If approved: "Generate Commitment & Proof" button enables
  → User clicks generate → outCommitment created

Step 3+: Repeat for each entity in chain

Final step: Click "Export On-Chain Data"
  → JSON of {commitments, proofs, approvalSigs, nullifiers} — NO amounts
  → "Copy & Open Verifier" transfers JSON to verifier tab
```

### Verifier Tab

```
User pastes on-chain JSON → clicks "Verify with Groth16"
For each record, checks:
  1. Proof structure (pi_a, pi_b, pi_c present)
  2. Elliptic curve = bn128
  3. π_A · π_B · π_C point validity
  4. Approval signature present (or root node)
  5. Chain linkage: inputCommitment[i] === outputCommitment[i-1]
  6. Output commitment format (0x prefix, 66 chars / 32 bytes)
  7. Nullifier uniqueness (no replay)
  8. Groth16 pairing equation (simulated)
```

## 6. Key Functions in app.js

| Function | Purpose |
|---|---|
| `sha256(str)` | Async SHA-256 via `crypto.subtle`. Simulates Poseidon for POC |
| `randHex(n)` | Cryptographically random hex string via `crypto.getRandomValues` |
| `fakeProof()` | Generates Groth16-shaped proof with random values |
| `makeEntity(idx)` | Creates initial entity state object |
| `addEntity()` | Adds entity to chain, wires up inCommitment from parent |
| `setAmount(id, val)` | Updates amount state **without re-rendering** (preserves input focus) |
| `requestApproval(parentId)` | Parent checks privately, writes only sig to child state |
| `generateCommitment(id)` | Computes commitment, fakeProof, nullifier (leaf); cascades to child |
| `renderAll()` | Rebuilds entire entity list DOM from state |
| `buildCard(e)` | Renders a single entity card (private zone + public zone + approval banner) |
| `approvalBanner(e, idx)` | Renders the approval state banner between cards |
| `finalizeChain()` | Exports on-chain JSON (no amounts) |
| `runVerify()` | Runs all Groth16 verification checks against pasted JSON |

## 8. What Is and Isn't Simulated

| Aspect | POC (this app) | Production |
|---|---|---|
| Hash function | SHA-256 | Poseidon (ZK-friendly) |
| ZK proof | Random bytes in Groth16 shape | Real Groth16 via snarkjs + Circom |
| Approval signature | `randHex(32)` | ECDSA over secp256k1 or BLS12-381 |
| Chain state | In-memory JS + exported JSON | EVM smart contract (`ASLDelegationChain.sol`) |
| Threshold check | JS arithmetic in `requestApproval()` | ZK circuit constraint in Circom |
| Nullifier registry | Array in exported JSON | On-chain mapping in Solidity |
| Key management | None | HSM / MPC wallet |

**Everything structurally correct:** data flows, privacy boundaries, approval direction, what goes on-chain vs off-chain, rejection semantics — all faithful to a production system.

## 9. How to Extend

### Add a new entity role
Add to `PRESETS` array in `app.js`. Cards are built generically — name is the only differentiator.

### Plug in real Poseidon hash
Replace the `sha256()` function with `circomlibjs.buildPoseidon()`. The commitment call signature `commitment(value, blinding)` stays the same.

### Plug in real snarkjs proofs
Replace `fakeProof()` with:
```js
const { proof } = await snarkjs.groth16.fullProve(
  { amount, blinding, parentSig },
  'circuit.wasm',
  'circuit.zkey'
);
```

### Connect to a real smart contract
Replace the JSON export with ethers.js calls to `ASLDelegationChain.sol`. The on-chain record shape maps directly to the Solidity struct.

### Add real ECDSA signatures
Replace `randHex(32)` in `requestApproval()` with a real signing operation:
```js
const sig = await parentWallet.signMessage(ethers.utils.arrayify(childCommitment));
```

## 10. Privacy Invariants (Never Break These)

1. **Parent threshold never reaches child state.** `child.approvalSig` is the only thing written by `requestApproval()`. If you ever see `child.threshold`, `child.parentAmount`, or `child.receivedDelegation.amount` — that is a bug.

2. **Amounts never appear in on-chain export.** The `finalizeChain()` JSON must never include `amt` fields. Only `inputCommitment`, `outputCommitment`, `proof`, `approvalSig`, `nullifier`.

3. **`setAmount()` must never call `renderAll()`.** Rebuilding the DOM destroys the focused input element. Amount updates are state-only; DOM refreshes only on generate/approve/remove.

4. **`inCommitment` is public on-chain data — never clear it on amount change.** It's derived from the parent's committed state, not from the child's private inputs.
