## 2. Privacy Model

### The Core Problem
Two separate systems (Mastercard, PSP) need to jointly prove a constraint without either system revealing its private value to the other or to the chain.

### The Solution: C_delta Linking

```
On-chain (public — just hashes):
  C_before   = Poseidon(MC.remaining_before, b1)
  C_after    = Poseidon(MC.remaining_after,  b2)
  C_delta    = Poseidon(delta, b_delta)          ← commitment to transferred amount
  C_amount   = Poseidon(PSP.amount, b3)

Off-chain (bilateral — MC tells PSP only):
  delta, b_delta   ← PSP uses to prove C_amount commitment matches C_delta

What the chain verifies:
  - Upstream proof:   C_before, C_after, C_delta are consistent with conservation
  - Downstream proof: C_amount, C_delta are consistent (PSP's amount == delta)
  - C_delta matches in BOTH proofs — this is the cryptographic link
  - Neither proof reveals the actual values
```

### What Each Party Knows

| Party | Knows | Never Knows |
|---|---|---|
| Mastercard | own total (1000), own remaining, delta (300) | PSP's internal details |
| PSP | own amount (300), delta (300) + b_delta from MC | MC's total (1000) or remaining (700) |
| Chain | C_before, C_after, C_delta, C_amount, two proofs | Any actual amount |
| Public | Same as chain | Any actual amount |

## 4. Circuits

### allocation_upstream.circom

**Purpose:** Mastercard proves their remaining decreases correctly.

**Private inputs** (never leave MC's system):
- `remainingBefore`, `remainingBeforeBlinding`
- `remainingAfter`, `remainingAfterBlinding`
- `delta`, `deltaBlinding`

**Public inputs** (go on-chain — just hashes):
- `commitmentBefore` — current remaining commitment
- `commitmentAfter` — new remaining commitment
- `commitmentDelta` — commitment to the transferred amount

**Constraints:**
1. `Poseidon(remainingBefore, remainingBeforeBlinding) == commitmentBefore`
2. `Poseidon(remainingAfter, remainingAfterBlinding) == commitmentAfter`
3. `Poseidon(delta, deltaBlinding) == commitmentDelta`
4. `remainingBefore - remainingAfter == delta` (conservation)
5. `remainingAfter >= 0` (no overdraft)
6. `delta > 0` (positive allocation)

### allocation_downstream.circom

**Purpose:** PSP proves their amount equals the delta from MC.

**Private inputs** (PSP's system + delta opening from MC):
- `amount`, `amountBlinding`
- `delta`, `deltaBlinding` ← received from MC via secure channel

**Public inputs**:
- `commitmentAmount` — PSP's amount commitment
- `commitmentDelta` — must match upstream's `commitmentDelta`

**Constraints:**
1. `Poseidon(amount, amountBlinding) == commitmentAmount`
2. `Poseidon(delta, deltaBlinding) == commitmentDelta`
3. `amount == delta`

## 5. Smart Contract

### ASLDelegationChain.sol

**`createRoot(amountCommitment, remainingCommitment)`**
- Root entity (Mastercard) creates initial commitments
- No proof required — self-authorised
- Returns `nodeId`

**`allocate(parentId, newParentRemainingCommitment, commitmentDelta, upProof..., childAmountCommitment, childRemainingCommitment, downProof...)`**
- Verifies upstream proof against `[commitmentBefore, commitmentAfter, commitmentDelta]`
- Verifies downstream proof against `[commitmentAmount, commitmentDelta]`
- **Critical:** `commitmentDelta` must appear in BOTH proofs — the contract checks this implicitly by using the same value for both verifier calls
- Updates parent's `remainingCommitment` on-chain
- Creates child node
- Emits `NodeAllocated` event

## 6. Setup and Deployment

### One-time setup (run on Hostzinger):

```bash
npm install
./scripts/setup.sh
# Takes ~10 minutes — downloads ptau, compiles circuits, generates keys
```

### Deploy to Sepolia:

```bash
cp .env.example .env
# Fill in SEPOLIA_RPC_URL and DEPLOYER_PRIVATE_KEY
npx hardhat run scripts/deploy.js --network sepolia
# Writes frontend/config.js with contract address automatically
```

### Serve frontend:

```bash
npx serve frontend/
# Open http://localhost:3000
# Connect MetaMask to Sepolia
```

## 8. Privacy Invariants

1. **Parent's total never reaches child state.** Child receives only `(delta, deltaBlinding)` — enough to prove their amount matches, not enough to infer parent's total.

2. **Amounts never appear on-chain.** The contract stores only `amountCommitment` and `remainingCommitment`. `commitmentDelta` links proofs but is itself a hash of the delta.

3. **setAmount() never calls renderAll().** Rebuilding DOM kills the focused input.

4. **remainingCommitment updates after every allocation.** `parent.remainingCommitment` must be recomputed with `parentRemAfter` in `runAllocation()`.

5. **Both proofs must share the same C_delta.** If they don't, one of the two verifier calls fails and the transaction reverts.
