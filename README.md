# ASL ZK Delegation Chain

> **Privacy-preserving payment delegation using real Zero-Knowledge proofs.**
> Real Groth16 · Real Poseidon · Real Sepolia smart contract · Nothing public on-chain except cryptographic commitments.

---

## What This Is

Traditional payment delegation looks like this:

```
Mastercard (limit: $10,000) → PSP (limit: $3,000) → Business (limit: $1,000) → Agent → Merchant
```

Every party in this chain can see every other party's limits. A PSP knows Mastercard's threshold. A business knows the PSP's ceiling. This creates competitive sensitivity and privacy issues at every level.

**This system eliminates that entirely.**

Using Zero-Knowledge proofs, each entity in the chain can prove their allocation is valid — without revealing their amount to the chain, to downstream parties, or to anyone observing the blockchain. The only things that go on-chain are cryptographic commitments (sealed envelopes) and mathematical proofs that the envelopes were filled correctly.

---

## The Privacy Model

### What goes on-chain (public)

```
amountCommitment    = Poseidon(amount, blinding)
remainingCommitment = Poseidon(remaining, blinding)
commitmentDelta     = Poseidon(delta, deltaBlinding)
proof_upstream      = Groth16 proof (cryptographic bytes)
proof_downstream    = Groth16 proof (cryptographic bytes)
```

No amounts. No limits. No values. Only hashes and proofs.

### What stays off-chain

```
Mastercard: own total (1000), own blinding factors, own remaining (700)
PSP:        own amount (300), own blinding factors
```

### The bilateral handshake

When Mastercard allocates 300 to PSP, Mastercard shares `(delta=300, deltaBlinding)` with PSP via a secure off-chain channel. PSP uses this to prove their commitment matches — without ever learning Mastercard's total of 1000 or remaining of 700.

### What the chain verifies

```
Upstream proof proves (in Mastercard's circuit):
  Poseidon(remaining_before, b1) == C_before           ← valid opening of on-chain commitment
  Poseidon(remaining_after,  b2) == C_after            ← valid new remaining commitment
  Poseidon(delta, b_delta)       == C_delta            ← valid commitment to transferred amount
  remaining_before - remaining_after == delta          ← conservation constraint
  remaining_after >= 0                                 ← no overdraft

Downstream proof proves (in PSP's circuit):
  Poseidon(amount, b3)     == C_amount                 ← valid opening of PSP's commitment
  Poseidon(delta, b_delta) == C_delta                  ← delta commitment matches upstream
  amount == delta                                      ← PSP claims exactly what MC allocated

Chain checks:
  Both proofs are valid ✓
  C_delta is the same value in both proofs ✓          ← cryptographic link — no amounts needed
```

The `C_delta` value is the bridge. It links both proofs on-chain without revealing what delta actually is.

## How It Works — Step by Step

### Step 1: Mastercard creates the root node

Mastercard enters their internal threshold (e.g. 1000). The system computes:
```
amountCommitment    = Poseidon(1000, random_blinding_1)
remainingCommitment = Poseidon(1000, random_blinding_2)
```
Both are submitted to the `ASLDelegationChain` contract via `createRoot()`. The contract stores the hashes. The number 1000 never appears anywhere on-chain.

### Step 2: PSP requests an allocation

PSP independently decides their own amount (e.g. 300). They do not ask Mastercard "can I have 300?" — they simply decide it.

The system then runs **two circuits simultaneously**:

**Mastercard's circuit (`allocation_upstream.circom`)**
Mastercard proves, using only their private values, that their remaining decreases by exactly the allocated delta:
```
Private witness: remaining_before=1000, remaining_after=700, delta=300, all blindings
Proves: conservation holds, no overdraft, all commitments valid
Output: proof_upstream + C_before + C_after + C_delta
```

Mastercard then shares `(delta=300, deltaBlinding)` with PSP via the secure off-chain channel. PSP now knows their allocation is 300. They do not know Mastercard's total or remaining.

**PSP's circuit (`allocation_downstream.circom`)**
PSP proves, using their own values plus the delta opening they received:
```
Private witness: amount=300, amountBlinding, delta=300, deltaBlinding (from MC)
Proves: their commitment is valid, their amount equals the delta
Output: proof_downstream + C_amount + C_delta
```

### Step 3: Both proofs submitted to Sepolia

The `allocate()` function on the contract:
1. Verifies the upstream proof against `[C_before, C_after, C_delta]`
2. Verifies the downstream proof against `[C_amount, C_delta]`
3. Checks that `C_delta` is the same value in both calls — this is the cryptographic link
4. Updates Mastercard's `remainingCommitment` on-chain
5. Creates PSP's allocation node

If either proof is invalid, or if `C_delta` doesn't match, the transaction reverts. Nothing is written.

### Step 4: Chain continues

PSP now has their own `amountCommitment` and `remainingCommitment` on-chain. The same process repeats when PSP allocates to a Business, a Business to Agents, and so on. Each allocation runs two proofs and updates one `remainingCommitment`.

## Setup Guide

### Prerequisites

```bash
# On your server (Ubuntu 22.04+)
node --version    # 18+
npm --version     # 9+
git --version
```

### 1. Clone and install

```bash
git clone https://github.com/abhinavasr/ZK-Chain-WebApp.git
cd ZK-Chain-WebApp
npm install
```

### 2. Run one-time circuit setup

This compiles the Circom circuits, downloads the Powers of Tau ceremony file (public, from Hermez), generates proving and verification keys, exports Solidity verifier contracts, and copies browser artefacts to `frontend/public/`.

```bash
chmod +x scripts/setup.sh
./scripts/setup.sh
```

**This takes approximately 10 minutes.** It only needs to run once. The generated files in `build/` and `frontend/public/` are reusable across all deployments.

What setup.sh does internally:
```
1. Installs circom compiler binary
2. Copies circomlib files (poseidon, comparators) to circuits/lib/
3. circom circuits/allocation_upstream.circom   → build/allocation_upstream.wasm + .r1cs
4. circom circuits/allocation_downstream.circom → build/allocation_downstream.wasm + .r1cs
5. Downloads powersOfTau28_hez_final_12.ptau (Hermez ceremony, public)
6. snarkjs groth16 setup → build/upstream.zkey + build/downstream.zkey
7. snarkjs zkey export verificationkey → build/upstream_vk.json + build/downstream_vk.json
8. snarkjs zkey export solidityverifier → contracts/UpstreamVerifier.sol + DownstreamVerifier.sol
9. Copies .wasm + .zkey + _vk.json to frontend/public/
```

### 3. Get Sepolia test ETH

You need a small amount of Sepolia ETH to deploy contracts and submit transactions.

- Alchemy faucet: https://sepoliafaucet.com
- Infura faucet: https://www.infura.io/faucet/sepolia
- Chainlink faucet: https://faucets.chain.link/sepolia

### 4. Configure environment

```bash
cp .env.example .env
```

Edit `.env`:
```env
# Sepolia RPC — free from Infura, Alchemy, or QuickNode
SEPOLIA_RPC_URL=https://sepolia.infura.io/v3/YOUR_PROJECT_ID

# Deployer wallet private key — must have Sepolia ETH
DEPLOYER_PRIVATE_KEY=0x...

# Etherscan API key for contract verification (optional)
ETHERSCAN_API_KEY=
```

> ⚠️ Never commit `.env` to git. It is in `.gitignore`.

### 5. Deploy contracts to Sepolia

```bash
npx hardhat run scripts/deploy.js --network sepolia
```

This deploys three contracts:
- `UpstreamVerifier.sol` — verifies Mastercard's circuit proofs on-chain
- `DownstreamVerifier.sol` — verifies PSP/child circuit proofs on-chain
- `ASLDelegationChain.sol` — main logic, holds allocation state

After deployment, `frontend/config.js` is automatically written with all contract addresses.

### 6. Serve the frontend

```bash
npx serve frontend/
```

Open `http://localhost:3000` in a browser with MetaMask installed and connected to Sepolia testnet.

## Using the App

### Chain Builder tab

1. **Enter Mastercard's amount** (e.g. 1000) in the first card
2. Click **"Commit to Chain"** — Poseidon commitments are computed and submitted to Sepolia via `createRoot()`
3. Click **"Add Entity"** to add PSP
4. **Enter PSP's amount** (e.g. 300) — PSP decides this independently
5. Click **"Prove & Submit"** — the system:
   - Runs Mastercard's upstream circuit (inside your browser)
   - Mastercard shares delta opening with PSP (simulated secure channel)
   - Runs PSP's downstream circuit
   - Verifies both proofs locally via snarkjs
   - Submits both proofs to `allocate()` on Sepolia
   - Both proofs are verified on-chain by the EVM verifier contracts
6. Repeat for each entity in the chain

### Chain Explorer tab

Shows live on-chain state from Sepolia — all allocation events with their commitments. Demonstrates that only hashes appear on-chain, never amounts.

## Circuits

### allocation_upstream.circom

Proves the conservation constraint from the upstream (parent) party's perspective.

**Signals:**
```
Private:  remainingBefore, remainingBeforeBlinding
          remainingAfter,  remainingAfterBlinding
          delta,           deltaBlinding

Public:   commitmentBefore   ← must match current on-chain value
          commitmentAfter    ← new value to publish on-chain
          commitmentDelta    ← links to downstream proof
```

**Constraints enforced:**
```
Poseidon(remainingBefore, remainingBeforeBlinding) === commitmentBefore
Poseidon(remainingAfter, remainingAfterBlinding)   === commitmentAfter
Poseidon(delta, deltaBlinding)                     === commitmentDelta
remainingBefore - remainingAfter                   === delta
remainingAfter                                     >= 0
delta                                              > 0
```

### allocation_downstream.circom

Proves the child's allocation is valid and matches the upstream delta.

**Signals:**
```
Private:  amount,  amountBlinding
          delta,   deltaBlinding   ← received from parent via secure channel

Public:   commitmentAmount   ← PSP's commitment to publish on-chain
          commitmentDelta    ← must match upstream's commitmentDelta
```

**Constraints enforced:**
```
Poseidon(amount, amountBlinding) === commitmentAmount
Poseidon(delta, deltaBlinding)   === commitmentDelta
amount                           === delta
```

## Smart Contract

### ASLDelegationChain.sol

**`createRoot(uint256 amountCommitment, uint256 remainingCommitment) → bytes32 nodeId`**

Root entity creates initial on-chain commitments. No proof required.

**`allocate(bytes32 parentId, uint256 newParentRemainingCommitment, uint256 commitmentDelta, uint[2] upPiA, uint[2][2] upPiB, uint[2] upPiC, uint256 childAmountCommitment, uint256 childRemainingCommitment, uint[2] downPiA, uint[2][2] downPiB, uint[2] downPiC) → bytes32 childId`**

Submits both proofs and allocates to a child entity:
- Verifies upstream proof against `[commitmentBefore, commitmentAfter, commitmentDelta]`
- Verifies downstream proof against `[commitmentAmount, commitmentDelta]`
- `commitmentDelta` must be identical in both — this is the on-chain link
- Updates parent's `remainingCommitment`
- Creates child node

**`getNode(bytes32 nodeId) → Node`**

Returns the on-chain state of a node (commitments only, no amounts).

## Limitations of This POC

| Limitation | Impact | Production fix |
|---|---|---|
| Single contribution to trusted setup | Slightly weaker security guarantees | Full multi-party ceremony (e.g. Hermez ceremony with 1000+ contributors) |
| Delta shared as plaintext between parties | MC and PSP know each other's amounts | Real MPC joint proving (DIZK, MP-SPDZ) — eliminates bilateral disclosure |
| Secure channel simulated in browser | Not a real encrypted channel | HSM-to-HSM / TLS mutual auth / Signal protocol |
| No nullifiers yet | Potential replay at merchant level | Poseidon-based nullifiers, on-chain mapping |
| No gas optimisation | Higher transaction costs | Batch proofs, recursive SNARKs (PLONK/STARK) |
| Browser proof generation (~30s) | Slow UX | Native prover (Rust), WebAssembly optimisation |

## Key Concepts Glossary

**Commitment** — A cryptographic hash of a value and a random blinding factor: `Poseidon(value, blinding)`. Hides the value while binding the prover to it. Cannot be reversed without the blinding factor.

**Blinding factor** — A random number that makes two identical values produce different commitments. Prevents linking commitments to known values.

**Groth16** — A zero-knowledge proof system producing proofs of ~192 bytes that can be verified on-chain in ~215,000 gas. Requires a trusted setup ceremony per circuit.

**Poseidon** — A hash function designed to be efficient inside ZK circuits (~200 constraints vs SHA-256's ~20,000). Used for all commitments in this system.

**Conservation constraint** — The arithmetic rule `remaining_before = child_amount + remaining_after`. Enforced inside the ZK circuit — cannot be satisfied with invalid amounts.

**C_delta** — A commitment to the transferred amount. Appears in both the upstream and downstream proofs, linking them on-chain without revealing the value.

**Trusted setup** — A one-time ceremony that generates the proving and verification keys for a Groth16 circuit. The toxic waste from this ceremony must be destroyed. More contributors = more secure.

**Powers of Tau** — The first phase of the Groth16 trusted setup, independent of any specific circuit. Reusable across circuits up to a maximum size. This project uses the Hermez ceremony output.
